# suPiposition: Design of a High-Performance π Calculator

**Status: design specification.** At the time of writing, the program had not yet been implemented or measured. Every performance figure is an analytical estimate, and every arithmetic result described as "verified" was confirmed by exact computation.

**Target platforms: processors at the x86-64-v4 level and later, and Arm processors at Armv9.2-A and later.** The portable program runs on any CPU under Linux, Windows, or macOS; the hand-written assembly is written for these two targets.

## 1. Summary

suPiposition computes π with the Chudnovsky series and binary splitting, the method used in every recent record computation. It is designed to outperform the program that holds the current record, y-cruncher v0.8.7 Build 9547, and it is released only when it does so (Section 15). Five design elements support that expectation: three that improve performance, listed in order of expected effect, and two that keep the program a single program for every system.

1. **Smaller operands.** A common factor with a closed form is divided out of the splitting recurrence at the levels selected by the planner (Section 10). The largest operands are 1.6–2.3× smaller than in plain binary splitting, and the splitting work decreases by a fifth to a third in the analytical model, with the cost of the divisions included. Q is stored without its trailing zero bits (Section 4).
2. **Reduced memory traffic.** A large product that fits one grid is computed by a three-sweep tiled transform that writes every array of transform data to memory once and reads it back once, bit-packed at rest where memory bandwidth is the limiting resource (Section 5). Memory bandwidth constrains a 256-core processor nearly as much as arithmetic does, and storage constrains every run larger than RAM.
3. **Exact arithmetic on the vector multiply-add units.** Large products use a number-theoretic transform whose modular reductions are double-precision fused multiply-adds, with eight residues per 512-bit register on x86-64-v4 and two per 128-bit register on Arm. Every processor of the two targets provides this capability, and the arithmetic is exact. The faster floating-point transform used for cache-sized products is verified on every product (Section 11).
4. **One reference machine, eight percentages.** suPiposition is written for a machine with 2⁶⁴ cores, 2⁶⁴ threads, and 2⁶⁴ bytes each of L1, L2, L3, RAM, VRAM, and SSD. A real system is described by its percentage of that machine in each of the eight resources and by the speeds measured on it, and every size and count is derived from that description at run time. A single program therefore fits a desktop, a 256-core server, and a machine larger than any built today (Section 6). It uses all of a system's cores, threads, caches, RAM, and VRAM, fastest first. VRAM serves as storage only: all computation is performed on CPU cores, and graphics cores, discrete or integrated, are excluded.
5. **Assembly only in leaf loops, one file per architecture.** A single portable Rust program, identical on every CPU, calls 24 leaf routines, the kernels, through a table. A single file per architecture may replace any of the 24: `x86_64.s`, written to the x86-64-v4 level, and `aarch64.s`, written to Armv9.2-A. Each serves every processor at its level or later (Sections 7 and 8). Without such a file, the same program runs on its portable reference kernels.

The code is intended to be elegant and minimalist, and Section 9 states those properties as rules. It is also intended to be improved over many edits by language models. The source is therefore divided into small components with boundaries that the compiler enforces, and an edit is accepted only when it is correct at every scale and either improves performance or is a repair (Section 15).

## 3. Computational Pipeline

| Stage | Method | Work (analytical model, 10¹¹ digits) |
|---|---|---|
| Series | Chudnovsky with reduced binary splitting (Section 4) | 87% |
| Finish | π = 4270934400·Q·z, where z = 1 / (√10005·(13591409·Q + T)) is obtained from one Newton iteration for an inverse square root, which also performs the division | 6% |
| Convert | Binary to decimal, top down; each node is one middle product (a product of which only the middle part is kept) by a power of ten whose transform is cached per level; vectorized leaf | 7% |
| Write | 19 digits per 64-bit word, or text | I/O only |

**The finish as one iteration.** Let A = 13591409·Q + T. The iteration for z starts from a double-precision estimate and doubles its precision at every step. A step forms u = A·z and the residual ρ = 1 − 10005·u², and corrects both by it: z ← z + z·ρ/2 and u ← u + u·ρ/2. The corrected u is the upper part of the next step's u, so the next A·z is a wrapped product (Section 11): computed one limb longer than the step, it supplies the remainder. The transforms of z and of ρ each serve two products, and multiplication by 10005 is one pass of the kernel `mul_1` (Section 7). The program's other divisions are exact and are performed from the low end (Section 4), and the conversion uses only products.

Verified by exact computation at 28,363 digits: the result matches, in every bit, a reference computed by integer square root and division. In 1,480 runs on numbers of up to 94,240 bits, the corrected u and a product wrapped 2 to 16 bits longer than the step gave u exactly at every step. Counted in transforms of π's length, the iteration takes 24 where a separate square root and division would take 27. A step costs ten transforms of its own length: three for A·z, three for u², whose two transforms are one and a half times as long, and two for each correction. The last step has no subsequent u to correct, so it costs eight, and the steps before it, which double in length, cost ten together. The product by Q, three transforms at twice the length, adds six.

**The conversion, exact at every node.** A node holds a fraction: its digits, with a guard limb below them. Its product with a power of ten has the left half's digits on top, as a whole number, and the right half's fraction under them; the left half is converted from the node's own fraction, truncated to its length. A truncated fraction can give an incorrect digit only within its guard of a whole number, so each left half's fraction is first moved half a guard toward the middle of its digits: up where the right half's fraction is under one half, and down where it is over. Every left half then gives exactly the whole number on top of its node's product, which is how the conversion is verified (Section 11). The last digits of the number lie in no left half, so the run converts that many more than are requested and discards them, and where they come out all zeros or all nines, it reports its last digits as in doubt.

Verified by exact computation on numbers of 3,000 digits: every left half was exact and every retained digit correct in 4,300 conversions, 4,000 of them of numbers with runs of zeros or nines placed inside. Of 3,223 numbers that end in zeros or nines, 136 gave an incorrect retained digit, and each of those was reported as in doubt.

## 4. Reduced Binary Splitting

Binary splitting sums the series by merging adjacent blocks of terms. A block (a, b] carries three integers: P and Q, the products over its terms of the numerators p(k) = −(6k−5)(2k−1)(6k−1) and the denominators q(k) = 10939058860032000·k³, and T, the block's sum scaled by Q. A single term k has P = p(k), Q = q(k), and T = (13591409 + 545140134·k)·p(k). A merge is P = P₁P₂, Q = Q₁Q₂, T = Q₂T₁ + P₁T₂. The whole series is the block that starts after term 0, and Section 3 turns its Q and T into π.

The cost lies in Q: the k³ adds 3·log₂ k bits per term, although almost all of it cancels against P. At the root of a run of world-record size, Q and T each carry about 182 bits per term where 62 would suffice.

**Closed form.** Write v_r(x) for the exponent of the prime r in x, and let e_r(L) = v_r(L!) − ⌊log_r L⌋. Define

R_L = 3^(e₃(L)) × ∏ over primes r ≥ 5 of r^(3·e_r(L)).

Then R_L divides P, Q, and T of every block of L consecutive terms, wherever the block starts.

*Proof sketch.* For r ≥ 5, the steps of the progressions 6k−5, 2k−1, and 6k−1 are coprime to r, so any j consecutive terms of each contain at least v_r(j!) factors of r; so do j consecutive values of k. A term of T is a product of j terms on the P side and L−j on the Q side, so it carries at least 3·[v_r(j!) + v_r((L−j)!)] = 3·[v_r(L!) − v_r(C(L, j))] factors of r, and v_r(C(L, j)) ≤ ⌊log_r L⌋ by Kummer's theorem. For r = 3, only 2k−1 contributes on the P side, hence the single exponent.

**Application.** The tree is balanced, so every node at a level has the same length L, and after a dividing level the triple is (P, Q, T)/R_L. The factor to remove at a dividing level is R_L over what its blocks have already shed: R_L / R_{L/2^m}^(2^m) when the last division was m levels below, about 3m bits per term. B_L = R_L / R_{L/2}² is the case m = 1. The factor is one odd integer per level. Because the division is exact and the factor is odd, it is performed from the low end (Hensel division), in one of two forms. One is a sequential pass over the number, a span of limbs (the 64-bit words of a number) at a time, built from short products (products of which only the low part is computed). The other is one product at twice the quotient's length with the cached transform of the factor's inverse, shared by every node of the level. The planner (Section 10) prices both for each dividing level.

The reduction requires four things: the primes up to L, from a segmented sieve; their exponents, from Legendre's formula; the product of those prime powers, which is the level's factor; and the inverse of that factor modulo a power of two. The last two are built once per dividing level and are counted in its cost.

**Verified** with exact integer arithmetic, on blocks starting at term 0:

| Block length L | Bits per term of Q, plain | After dividing by R_L | With the true gcd |
|---|---|---|---|
| 64 | 67.2 | 61.5 | 57.3 |
| 256 | 73.0 | 61.9 | 57.7 |
| 1,000 | 78.9 | 62.1 | 57.8 |

All 40 blocks tested, with lengths from 4 to 1,000 and random starts up to 10⁷, were divisible. B_L is an integer for every even L, again by Kummer's theorem: where L has one more digit than L/2 in base r, adding L/2 to itself carries. It was verified for L = 2³ … 2¹⁴, where its size settled at 3.0 bits per term. For the first n terms of the series, the plain size follows 53.3 + 3·log₂(n/2.718) bits per term: 127 at 10⁹ digits, 147 at 10¹¹, 182 at 3×10¹⁴. The reduced size of a block that starts at term 0 stays near 62. A short block deep in the series sheds less, because the factor depends only on the block's length: blocks of 128 to 2,048 terms that start a few million terms in measured 100–110 bits per term.

**Schedule.** Leaves have one length for the whole tree. The planner takes the smallest power of two that divides the term count into leaves whose working set, which is the two half-triples and their merge, fits the smallest L1 share among the workers (Section 6). The leaf length is the term count divided by that power, rounded up, so the tree carries less than one extra term per leaf. Inside a leaf, plain binary splitting is used. Above the leaves, the planner chooses the levels that divide. By a count of transforms, a division costs about as much arithmetic as the level's own merge and, where it is performed as a single product, somewhat more traffic. In return, every product above it is 3 bits per term smaller for each level since the last division. A merge's size depends only on the last division below it, so the planner finds the set of dividing levels that gives the series the least time by a shortest-path computation over the levels. In the count, that is about every sixth level, with the six or seven levels nearest the root left undivided: the root has nothing above it to benefit, a level just below it has too few levels above it to repay a division, and the factor and its inverse are shared by few nodes there.

**Merge.** Sharing forward transforms between the four products, and adding the two halves of T before a single inverse, reduces a merge from nine full-length transforms to seven. The three short ones for P are unchanged. This arrangement is called the fused merge. Its sum takes one more bit of room in the product of the transform's primes (Section 5) than a single product does, which the planner counts. A block that ends the series carries only Q and T, so the root and the last node of each level skip P's product and its division.

**Q without its zero bits.** The constant in q(k) is divisible by 2¹⁵, and k³ adds three zero bits for each factor of two in k, so the Q of a block of L terms ends in at least 15L + 3(L − s) zero bits, where s is the number of one bits in L: about 18 per term. They are kept as a shift count, and only the rest of Q is stored, multiplied, and divided. The two products that form T are then computed separately, each at the length its own operands require, instead of fused at the full length.

Verified with exact arithmetic on pairs of 512-term blocks, each divided by R₅₁₂. The figure is transform work relative to the fused merge, with the separate form counted as five transforms at the length of Q₂T₁ without the zero bits, three at the length of P₁T₂, and the three for P.

| Where the block starts | Separate products |
|---|---|
| Term 0 | 0.90 |
| 8 block lengths in | 0.94 |
| 32 block lengths in | 0.95 |
| 512 block lengths in | 0.97 |
| 32,768 block lengths in | 1.00 |

The planner selects the cheaper form for each node from the operand sizes: separate products out to about 80,000 block lengths from the start of the series for blocks just divided and about half as far for each level since, and the fused merge beyond.

**Expected effect (a count of transforms, to be measured).** With every division priced, splitting work decreases by 20% at 10⁹ digits, 25% at 10¹¹, and 33% at 3×10¹⁴, and the memory traffic of the levels that leave the caches decreases by about a third. Root operands are 1.6–2.3× smaller: about 80 bits per term with the six or seven levels nearest the root undivided, where fully reduced is 62. The count takes seven transforms per merge at the length of Q₂T₁ and three at the length of P₁P₂, two per divided number at twice the quotient's length, the factor and its inverse once per dividing level, and sizes from the closed form. Separate products take one to three points more off the work, and about 5% off the top eight levels, which are the ones that leave RAM in a large run.

## 5. Multiplication

| Method | Range (crossovers calibrated at startup) | Arithmetic | Exactness |
|---|---|---|---|
| Basecase | Up to the first crossover, typically a few dozen 64-bit limbs | Classical multiplication on limbs | Exact |
| Karatsuba | Up to the second crossover, typically somewhat over a hundred limbs | Recursion in portable code | Exact |
| FFT | Products whose transform fits the worker's share of L2 (Section 6) | Complex doubles, weighted convolution | Verified on every product against its check word and a bound on its largest rounding error; a product over the bound, or one whose check word fails and that is beyond correction, is recomputed with the NTT (Section 11) |
| NTT | Everything larger | 3 to 18 primes below 2⁵⁰, as many as the planner finds fastest; residues held as integer-valued doubles; reduction by fused multiply-add | Exact |
| Split | Products over 1.82×10¹⁵ bits | Halving, or an outer transform over the numbers modulo 2^m + 1, with NTT products inside | Exact |

**Why primes under 2⁵⁰ in doubles.** The product of a 50-bit residue and a 50-bit constant is recovered exactly from one multiply and one fused multiply-add, and the quotient estimate is off by at most one. Every x86-64-v4 processor does this on eight residues per 512-bit register, and every processor of the Arm target on two per 128-bit register. The portable version is the same arithmetic in plain Rust. Compilers vectorize it unaided where the build's baseline has fused multiply-add, as the Arm baseline does; on the plain x86-64 baseline it is an exact library call, which is the cost of a single binary for every processor.

**Capacity, verified by computation.** The number of primes c·2^t + 1 below 2⁵⁰ is 65 for t = 40, 33 for 41, 18 for 42, 8 for 43, 3 for 44, and 0 for 45. A transform operates on an integer divided into coefficients of equal length. The eighteen primes at length 2⁴² multiply to 2^868.3 and carry a 1.82×10¹⁵-bit product in one transform, as 2⁴² coefficients of 413 bits, the most of any length; the eight at 2⁴³ carry 1.50×10¹⁵. A butterfly is the basic step of a transform: it combines two values with one modular multiplication. More primes at a shorter length take fewer butterflies per bit of product, about 9% fewer for eighteen at 2⁴² than for eight at 2⁴³, at the cost of a longer recombination, so the planner weighs the two. One transform holds the series at today's world-record size of about 3×10¹⁴ digits, where the largest product, in the separate form of Section 4, is about 1.6×10¹⁵ bits.

**The split.** A longer product takes the split, which has two forms. Halving divides the product in two and computes three half-size products, so each level costs half again as much as the product it replaces: 1.5, 2.25, and 3.4 times a single transform of the full length at one, two, and three levels. The outer transform divides each number into k parts and multiplies them as a polynomial over the numbers modulo 2^m + 1. There the roots of unity are powers of two, so its passes are shifts and additions, and its k inner products are NTT products of m-bit numbers, reduced modulo 2^m + 1 by taking their transforms at the odd roots of unity, which changes only the root tables the transform kernels are given. Verified with exact arithmetic for k from 4 to 64: the result is exact, and the inner products come to twice the product's own length at every k. This form therefore costs about twice a single transform at any size, plus one pass of shifts and additions per level of the outer transform. The planner prices both forms for each product. The last product of the finish, which is twice the length of π, takes one halving at today's world-record size.

**Layout of a large product.** Each prime's transform is treated as a grid. The rows a worker holds fill its share of L3, a tile fills its share of L2, and a group of butterflies inside a tile fills its share of L1 (Section 6). A grid that several workers sweep, and a product that any worker may take, are sized to the smallest share among those workers, as the series leaf is.

1. *Column sweep.* Tiles of a few adjacent columns are gathered into L2, transformed, and scattered. This sweep also splits the integer into residues, so it reads the compact integer and writes each residue array once.
2. *Row sweep.* A worker pulls one row of each operand into L3, finishes the forward transform tile by tile, multiplies pointwise (or forms the two-product sum of the T merge), starts the inverse, and writes one product row.
3. *Column sweep back.* This sweep also recombines the primes and propagates carries, so it reads the residues once and writes the compact product. A short pass stitches carries across tile boundaries.

For n-bit operands with residue arrays of S bits, about 6S + 4n bits cross memory: roughly 40n with 64-bit doubles at rest and 32n when residues are packed to 50 bits at rest and unpacked only inside the cache. Packing costs a few percent of extra compute and is enabled by the planner where memory bandwidth is the limiting resource. A transform too long for one grid at these sizes takes one more column sweep in each direction for each further level of the grid, and the planner selects the grid shape that takes the least time (Section 10).

## 6. One Reference Machine, Eight Percentages

**The reference machine.** suPiposition is written for an imaginary machine with 2⁶⁴ of each of eight resources: cores, threads, and bytes of L1, L2, L3, RAM, VRAM, and SSD. That is one more than a 64-bit register can count, so every 64-bit system, present or future, is below 100% of everything, and every count, length, and limb in the program is a 64-bit integer, the native width of the registers. The reference machine is the only upper bound on the size of a system. One transform has a length limit of its own, which the split removes (Section 5).

**The profile.** At startup, `platform` (Section 7) counts what the system has available of each resource, as a percentage of the reference machine. That count is the profile, with one entry per resource. Cores and threads are single percentages. RAM lists its memory (NUMA) nodes, each with its size and the threads nearest to it. Each cache level lists its caches, each with its size and the threads that share it. VRAM and SSD list their devices, each with its size and alignment. A percentage is the count itself, held as a 64-bit binary fraction, so it is exact and free to compute: the 96 cores of one EPYC 9686F are 96 parts in 2⁶⁴.

The profile is the only counted description of a system, and the calibration figures (Section 10) are the only measured one. Every figure that belongs to a particular system reaches the portable source and the assembly file through those two, at run time. Every size and worker count is derived from them and is itself a percentage of the reference machine, as is every percentage in the program. This is what makes the design modular and universal: one program, with one assembly file for each architecture, serves every system of the two targets, and a system with ten times the cores, cache, or memory has a profile ten times as large, all of it used, while ten times the storage holds a run ten times as large.

**All of it, fastest first.** A single rule determines how a system is used.

- *All of it.* suPiposition takes everything the profile reports of cores, threads, L1, L2, L3, RAM, and VRAM for the run, and of SSD what the run requires, wherever the SSDs stand in the order. The operating system and the GPU driver report what is available after setting aside what they require themselves. suPiposition reserves all of it at startup and pins each part as it is first touched, and everything it allocates is drawn from that reservation.
- *Fastest first.* Resources that serve the same purpose are used from fastest to slowest. Data resides in the fastest memory that has room, in the order L1, L2, L3, RAM, and then the extent devices of the store (Section 10), and a slower tier holds only what the faster ones have no room for. Room is committed by the plan (Section 10), soonest needed first, so the fastest tier always holds the data that will be needed next. Work is assigned to the fastest workers first. A run fills the tiers in order, so a small run ends in an early tier and a large one reaches them all.

| Resource | What the profile counts | Taken | What is sized to it |
|---|---|---|---|
| Cores | The CPU cores the operating system lets the process use, and only CPU cores | All | The cores that run workers |
| Threads | The hardware threads on those cores | All | The workers, one per thread |
| L1 data cache | The bytes in each cache | All | The working set of an inner loop: a leaf of the series, one group of butterflies |
| L2 cache | The bytes in each cache | All | The working set of a tile, which is what a worker gathers, transforms, and scatters in one step; every FFT product |
| L3 cache | The bytes in each cache | All | The rows a worker holds during the row sweep: operands in, product out |
| RAM, including unified memory | The bytes the operating system reports as available at startup | All | Numbers and transform buffers; in a run larger than RAM, the tile of the store being swept and the one in flight (below) |
| VRAM | The bytes the driver reports as available at startup on each discrete GPU | All | Extents, which are spans of bytes on an extent device (Section 10): numbers parked until they are needed, and residue arrays that RAM has no room for |
| SSD | The bytes free at startup on the devices or files the command line names | What the run requires | Extents that fit nowhere faster, and checkpoints |

- **Shares.** The operating system reports each cache's size and which cores share it. A cache's capacity is divided evenly among the workers on those cores, so the two workers of a two-thread core each have half of its L1 and L2. The workers' shares sum to the whole cache.
- **Working sets fill the caches.** What is sized to a worker's share of a cache is its whole working set at that level: the data and the constants its kernels read. The planner selects the largest size whose working set fits the share that the module `tier` (Section 7) gives it, so each cache is used as fully as the sizes allow. Each working set is one contiguous region on huge pages, which distributes evenly over the cache's sets. Data in transit is kept out of its way by two kernels (Section 7): `scatter` writes with non-temporal stores, which bypass the caches on x86-64 and request to on Arm, and `gather` prefetches with the non-temporal hint, which marks data as used once. How well each processor honors these is measured, and where it honors them poorly, the plan counts the data in transit as part of the tile's working set.
- **Order.** Caches and RAM are always in the same order. Workers are ranked by the measured throughput of their core, with every core's first thread ahead of any second thread. Where the operating system places threads itself, as macOS does on Apple's processors, the workers take its highest service class, and its placement stands in for the ranking. The extent devices are stripes of members, each member one SSD or the VRAM of one discrete GPU, and they are ranked by the transfer rate measured beside the sweep step (Section 10).
- **Missing or small tiers.** When a cache level is absent, or gives a worker at most what the level below it does, its role passes to that lower level. A system without a discrete GPU or without an SSD has 0% in that entry of its profile, and the same code handles it. Without an SSD, a run must fit in RAM and VRAM, and it keeps no checkpoint (Section 11).
- **Sizing is automatic.** Everything available is used, so every size is derived, and the command line specifies the digits, the output, and the storage devices (Section 7). What is available to a process is determined by the operating system, through processor affinity and memory limits, and that is where a run is confined if it must share a machine.

**The same structure at every boundary.** Each tier is a cache for the next. The sweep layout of Section 5 places groups of butterflies in L1 inside tiles in L2 inside rows in L3 inside RAM. One level up, the same routine sweeps an array that resides in the store one tile of the store at a time, which is the part of the array that is in RAM at once. Only the loading differs: the loader, which is part of the module `store` (Section 7), moves those tiles while the workers sweep (Section 10).

**VRAM for storage, CPU cores for computing.**

- *What counts.* Memory on a discrete GPU, which is physically separate from RAM. Integrated graphics are excluded: their memory is system RAM, which the profile already counts, and their cores are graphics cores. On a unified-memory system, where the CPU and the graphics share one pool, that pool is the RAM entry and the VRAM entry is 0%. Any part of the pool that firmware reserves for graphics is outside what the operating system reports, so it is outside the profile.
- *How it is accessed.* Through the Vulkan 1.4 interface of the GPU driver, loaded at run time if present. suPiposition allocates device memory, hands the driver its own page-aligned buffers (host-memory import), and submits buffer-to-buffer copies, many ranges to a submission (Section 10). The GPU's copy engine moves the bytes over the PCIe link by direct memory access, the way an SSD controller serves a direct read, and the CPU cores remain free for arithmetic meanwhile.
- *How computation is confined to CPU cores.* The profile counts CPU cores only, so all work is planned for CPU cores. A discrete GPU is opened with a single queue, taken from a family that offers transfer and neither graphics nor compute; such a family may also offer sparse binding. Vulkan accepts draw and dispatch commands only on queues that offer graphics or compute, so the queue suPiposition holds can copy bytes and do nothing else. Beyond opening the device and querying what it offers, the program's only GPU code is the extent interface's five calls (Section 10), which hold and move bytes. A discrete GPU is used only if its driver offers such a family, Vulkan 1.4, host-memory import, and the memory-budget query.
- *What it stores.* Extents, exactly as an SSD does. Checkpoints go to SSD only, because they must survive a restart.
- *What it is worth.* VRAM is slower than RAM, because every byte it takes crosses both a PCIe link and the memory channels, and it is far smaller than an SSD array. A GPU's VRAM joins whichever stripe it makes faster (Section 10), so it stands alone where it outruns the SSDs and adds its link to theirs where they are many. The smallest member sets a stripe's size, so VRAM matters most to a run that outgrows RAM by about as much as its stripe holds, and less as runs grow beyond that.
- *Verified on one machine.* A GeForce RTX 5070 on NVIDIA driver 621.24 reports Vulkan 1.4.357, a queue family that offers only transfer and sparse binding, host-memory import at page alignment, and the memory-budget query. That is everything this section relies on.

## 7. Program Structure and the Kernel Seam

```
suPiposition/
  engine/       portable Rust on the standard library alone; shares come from tier, sizes from plan, speed from kernels
                limb  fft  ntt  mul  splitting  newton  radix  tier  plan  par  arena  store  check  refk
  kernels/      exactly one assembly file per CPU architecture, named as the compiler names it
    x86_64.s            x86-64-v4 and later
    aarch64.s           Armv9.2-A and later
    build.rs  lib.rs    Rust glue, the same for every architecture
  platform/     linux/  windows/  macos/            the profile, thread placement, huge pages, direct I/O
                vram                                one GPU's memory as a member of a stripe (section 10); the same code on every OS
  cli/
```

The modules of `engine`:

| Module | Responsibility |
|---|---|
| `limb` | Numbers as 64-bit limbs; the basecase and Karatsuba products |
| `fft`, `ntt` | The two transforms (Section 5) |
| `mul` | Runs each product by the method and grid shape the plan chose |
| `splitting` | The series (Section 4) |
| `newton` | The finish (Section 3) |
| `radix` | The conversion to decimal |
| `tier` | The one place where the profile is turned into shares and worker counts (Section 6) |
| `plan` | The planner (Section 10) |
| `par` | The scheduler |
| `arena` | The three memory arenas, each a standard allocator (Section 10) |
| `store` | Extents, the stripes they lie on, and the loader (Section 10) |
| `check` | Check words, correction, and checkpoints (Section 11) |
| `refk` | A plain implementation of every kernel, which is both the fallback and the specification |

A seam is a narrow interface with interchangeable code behind it. There are two. The kernel table lets one assembly file stand in for the portable kernels. `platform` holds everything that requires the operating system, with one component each for Linux, Windows, and macOS, and GPU memory in `vram`.

`cli` is the command line. It takes the number of digits, the file to write them to and its format, the SSD devices or files the store may use, and, where those hold a record that the start does not resume from, the instruction to discard the records (Section 11). It also accepts a profile, with calibration figures, in place of the counted and measured ones, to plan or test for another system. It prints every report the program makes.

**Layout for speed and for iteration.** The four folders are four crates, Rust's units of compilation, in one workspace. The crate graph keeps `kernels` and `platform` out of `engine`'s reach, and a test build fails if `engine` names an architecture, an operating system, or inline assembly. `cli` joins the crates: it hands `engine` `supi_bind` from `kernels` and the interfaces from `platform`, so `engine` names neither. Each module is one file, and each file opens with its contract: what it takes, what it returns, the format its data is in, and what it guarantees about work and bytes moved. Contracts are checked by assertions in test builds. The division into crates costs nothing in speed, because release builds optimize the whole program as one (Section 12).

**One assembly file per architecture.** Everything written in assembly for a CPU architecture is in one file, `kernels/<architecture>.s`, complete in itself. This design specifies two such files, `x86_64.s` and `aarch64.s`. A port to another architecture adds one file named for it.

- *Selection.* At build time, the glue looks for the file named after the target architecture. If it is present, it is assembled into the program; otherwise, an empty `supi_bind` is compiled in its place. The file's presence is the only switch.
- *Contents, in the same order in every file.* A header stating the instruction-set level, a preamble of assembler macros, the CPU probe and `supi_bind`, the kernels it implements, by family, then read-only constants.
- *One file for every operating system.* The glue passes the target operating system to the assembler as a symbol. The preamble uses it to adapt symbol names, section names, the way the probe reads the system, and (on x86-64, where Windows and Unix pass arguments in different registers) the calling convention. Kernel bodies are written once.

**The 24 kernels.**

| Family | Kernels, in order | What they do, in the same order | Data |
|---|---|---|---|
| Limbs (6) | `add_n`, `sub_n`, `mul_1`, `addmul_1`, `mul_base`, `sqr_base` | Add two numbers; subtract them; multiply a number by one limb; do that and add the result into another number; the classical product; the classical square | 64-bit limbs, least significant first |
| FFT (6) | `fft_split`, `fft_fwd`, `fft_inv`, `fft_pmul`, `fft_pmuladd`, `fft_carry` | Divide an integer into coefficients; the forward transform; the inverse transform; the pointwise product; the pointwise sum of two products, for the fused merge; round back to an integer and propagate carries | Complex doubles. `fft_carry` also returns the largest rounding error seen and the product's check word. |
| NTT (8) | `ntt_split`, `ntt_fwd`, `ntt_inv`, `ntt_fwd_cols`, `ntt_inv_cols`, `ntt_pmul`, `ntt_pmuladd`, `ntt_crt` | Reduce an integer's coefficients modulo a prime; the forward passes inside a tile; the inverse passes inside a tile; the forward passes across a tile's columns; the inverse passes across them; the pointwise product; the pointwise sum of two products, for the fused merge; recombine the primes into an integer and propagate carries | Residues as doubles, one prime per call, except `ntt_crt`, which takes every prime and also returns the check word. |
| Movement (2) | `gather`, `scatter` | Copy strided or 50-bit-packed data into a dense tile; copy a tile back out | Strided or packed residues on one side, a dense tile on the other |
| Digits and check words (2) | `to_digits`, `check_n` | Convert binary words to decimal digits; compute the first check word of a span of limbs, or all three (Section 11) | Decimal digits, with their check word; limbs |

**Binding.**

1. `engine` fills the table with the reference kernels.
2. It calls `supi_bind(table, abi)`, the one symbol an architecture's assembly file exports. `table` is the table of 24 entries. `abi` is the version number of the table's layout, and a file binds only to the layout it was built for. The file's own probe examines the CPU and overwrites the entries it can serve; on a CPU below the file's instruction-set level, or under an operating system the file has no reading for, the reference entries remain.
3. `engine` runs each overwritten entry against its reference on random and edge-case inputs. A mismatch restores the reference entry and is reported.
4. `tier` turns the profile into shares and worker counts, and the planner calibrates, the non-temporal hints first (Sections 6 and 10).

**Rules that keep it modular.**

- `engine` is architecture-blind: naming an architecture and detecting features are the assembly file's responsibility.
- Kernels are leaves: pure functions of their arguments. Memory, threads, and state stay in `engine`, and system calls stay behind `platform`. Arguments are pointers, lengths, and plain constants, passed by the platform C calling convention.
- A kernel is system-blind. Every length it works on is an argument, set by the plan (Section 10), and a kernel is correct for every length its contract allows.
- A kernel's contract is its reference. Limb, NTT, movement, digit, and check-word kernels match it bit for bit, with residues fully reduced. The FFT family is held as a chain: split, forward, pointwise product or sum of two products, inverse, and carry together return the same limbs and check word as the reference chain, and the doubles in between are free to differ.
- The FFT family is bound, tested, and restored as one unit, and a file may implement any subset of the other 18.

## 8. The Assembly Files

`x86_64.s` has one body per kernel. `aarch64.s` has one for each of its six limb kernels, which use no vectors, and two for each of the other eighteen: a NEON body, and an SVE2 body for the processors that have SVE2. The table gives how each file uses its instruction set, with the NEON bodies in its last column.

| Kernels | `x86_64.s` | `aarch64.s` |
|---|---|---|
| Limbs | MULX with two independent carry chains (ADCX, ADOX), unrolled across the general registers. `mul_base` leaves them where its shorter operand has 14 to 64 limbs and its longer at most 128: both are split into 28-bit digits and multiplied eight per 512-bit register, and no carry is taken until the end. | MUL and UMULH for the two halves of each product, on one carry chain (ADCS), unrolled across the general registers |
| FFT | Four complex doubles per 512-bit register, with fused multiply-add throughout. `fft_carry` converts to integers eight at a time and tracks the largest rounding error with the DQ rounding instructions. | One complex double per 128-bit register, with fused multiply-add and the complex multiply-add of Armv8.3 throughout. `fft_carry` converts to integers two at a time and tracks the largest rounding error. |
| NTT | Eight residues per register. A modular multiply is two multiplies, two fused multiply-adds, one rounding, one add, and a masked correction, all branch-free. Radix-16 passes are held entirely in the 32 vector registers, so loads and stores are few. Prime recombination uses the same arithmetic. | Two residues per register. The modular multiply is the same, with its correction by compare and select, and the radix-16 passes are held in the 32 vector registers in the same way. Prime recombination uses the same arithmetic. |
| Movement | Variable shifts and permutes pack and unpack 50-bit residues; `gather` prefetches with the non-temporal hint, and `scatter` writes with non-temporal stores | Shifts and bit-field moves pack and unpack 50-bit residues; `gather` prefetches with the streaming hint, which is A64's non-temporal one, and `scatter` writes with non-temporal pair stores |
| Digits and check words | Vectorized digit conversion, which also returns the check word of its digits; the first check word by shifts and additions, since its modulus is 2⁶¹−1, and the two locating words of Section 11 by the NTT's modular multiply on the two halves of each limb | Digit conversion by multiply-high; the check words as in `x86_64.s` |

**Level of `x86_64.s`.** The file is written to x86-64-v4 (Section 2), and its limb kernels also require ADX. On an x86-64-v4 processor, the probe binds five of the six limb kernels where ADX is present, the other eighteen where the operating system saves the 512-bit registers, and `mul_base`, which uses both, where both hold. macOS enables that saving at a thread's first 512-bit instruction, so there the probe reads the capability flags that the system publishes in memory.

**Level of `aarch64.s`.** The file is written to A64 at Armv9.2-A, the newest version that the Apple M5 Ultra, the Apple M6, and NVIDIA's Vera share (Section 2). All three have NEON, its 128-bit vector set, and Vera's cores also have SVE2. The probe binds the SVE2 bodies on a processor that reports SVE2 and the NEON bodies on any other. Apple's processors report none: they have those instructions only inside the streaming mode of SME, which the file never enters. The file is assembled as `armv9.2-a+nosve`, with SVE2 enabled for the SVE2 bodies alone. On Linux the probe reads the identification registers, which the kernel answers for a user program, and on macOS the capability flags that the system publishes in memory.

**The SVE2 bodies.** They perform the same arithmetic as the NEON bodies, on registers whose length they read from the processor. One body therefore holds as many numbers per register as a processor provides: two at Vera's 128 bits, and more wherever the registers are longer. Predicates take the place of compare and select and end each loop without a scalar tail. `gather` and `scatter` use SVE2's own gather loads, scatter stores, and non-temporal loads and stores, and the digit conversion uses its 64-bit multiply-high.

**Written for the reference machine.** The kernels take 64-bit lengths, and every size and threshold reaches them as an argument (Section 7), so each file fits the reference machine and every system that is a percentage of it.

## 9. Elegance and Minimalism in the Code

The code is intended to be read end to end and trusted. Elegant means that one idea does the work of several. Minimalist means that everything in the source has a reason that can be stated in a sentence. Both are requirements of the design, maintained by these rules:

- **One mechanism per task.** One rule, all of it and fastest first, determines how every system is used. One sweep routine serves every boundary between tiers. One iteration performs the final square root and division. One extent interface serves VRAM and SSD. One table binds every kernel. One module, `tier`, turns the profile into every share. One set of check words protects every number, every stored piece, and every digit, and one ladder corrects whatever fails a check (Sections 10 and 11).
- **Counts that stay small.** 1 reference machine, 8 resources in a profile, 24 kernels, 1 assembly file per architecture, 1 body per kernel for each vector set its file serves, 1 library in the portable code, and 1 place that examines the CPU.
- **One code path for every processor.** Two systems differ only in their profiles and in the speeds the planner measures.
- **Every edit must pay.** An edit is accepted only when it improves performance or is a repair (Section 15).
- **Every kernel has a plain twin.** `refk` states in ordinary Rust what each kernel computes. The assembly is correct when it matches, so it can be all fast path.
- **Checks instead of caution.** Every fast path is tied to an exact reference (Section 11). That keeps the code short.

## 10. Planner, Scheduler, Memory, and Storage

**Calibration.** At startup, the planner takes the shares and counts that `tier` derives from the profile (Section 6) and measures the calibration figures:

- the throughput of each kernel on each core, of which that of `ntt_fwd` ranks the workers, or, where the operating system places the threads, on the workers as it places them (Section 6);
- the memory bandwidth, and the time of one sweep step (one tile gathered, transformed, and scattered), with every worker running;
- the crossovers between the methods of multiplication;
- the time of one operation of the sieve;
- how well the processor honors the non-temporal hints;
- for the store, whose members, extent devices, ranges, and batches are defined under Storage below, the transfer rate of each member with the workers idle, from which the stripes are formed, and for each extent device its transfer rate with the workers idle, its rate while every worker repeats the sweep step, the time of that step beside the transfer, and the smallest range from which a batch moves at those rates. Each rate is measured over a write and the read back.

The figures are kept with the profile's cores, threads, and caches; the build; and the set of kernels left bound after the startup test, and are reused while all three are unchanged. The memory bandwidth and the time of the sweep step are measured at every startup, and so are the figures of the store when the run may use it, because memory and members can change while the cores, threads, and caches stay the same.

**Plan.** For each product, the planner selects the method, the number of primes, the length of a coefficient, the grid shape, and the packed or unpacked rest format that minimize the product's time. Compute time is the arithmetic. Traffic time is the bytes that must cross a tier, divided by that tier's bandwidth. A worker gathers, computes, and scatters in turn, so a product's time lies between the larger of the two and their sum, and the planner places it between them from the measured time of the sweep step. A machine, or a phase of a run, is called compute-bound or traffic-bound according to which of the two is larger. The planner also selects the splitting levels that divide, the form of each division, and, for each node, the form of the merge (Section 4); the form of each split (Section 5); and which products are computed whole, wrapped, or in part (Section 11). The plan also commits the room in each tier, soonest needed first (Section 6). A plan is a deterministic function of the command line, the profile, and the calibration figures, and for a resumed run also of the checkpoint's record (Section 11). Before a run starts, the planner confirms that the SSDs hold what the run will require. A new run creates the output file at its full size, in place of any file of that name. A run that the system cannot hold, or whose output file cannot be created at its full size, does not start, and one that loses the room it requires ends, each with a report of what is missing.

**Transfers.** A transfer shares the memory channels with the workers, so each slows the other. The loader writes the last tile of the store back and reads the next one while the workers sweep the one in RAM, and a parked number moves while they work on others. The planner prices the part of such a transfer that the sweep covers at the rate beside the sweep step, and it prices the step at its time beside the transfer. What is left of a transfer when the sweep ends, and any transfer the workers wait for from its beginning, is priced at the rate with the workers idle. The plan fixes those parts.

**Scheduler.** Fork-join with work stealing, built on the standard library. One worker runs on every hardware thread for the whole run, and the loader of the store runs on a thread of its own, which sleeps while a batch moves. Below the depth at which the tree has sixteen times as many nodes as workers, a subtree runs on one worker, and stealing evens out the rest; above that depth, products are parallel across primes and tiles. An idle worker sleeps, and sleeping workers are woken in rank order (Section 6), so whenever there is less work than workers, the fastest have it.

**Memory.** `arena` manages three arenas that together hold the RAM in the profile, less the program's own stacks and heap, which are taken first: numbers, in one last-in first-out region per worker for the subtrees it runs alone and in plan-assigned regions above that depth; per-worker scratch, sized to the worker's cache shares; and shared transform buffers. All three are on huge pages, on the memory (NUMA) node nearest the workers that use them, and are first touched by those workers. Where the operating system refuses huge pages, the arenas use ordinary pages; where it refuses pinning, they remain unpinned; and either is reported. Each arena implements the standard allocator interface, which Rust 1.100.0 made stable for vectors and boxes, and those are all the arenas hold. Numbers and buffers are therefore ordinary vectors that are handed a reference to their arena.

**Storage.** The store is a list of extent devices. It holds what RAM has no room for, and a run that uses it is called out of core.

- *Members and stripes.* A member is one SSD, which is a raw NVMe device or a preallocated file, or the VRAM of one discrete GPU. An extent device is a stripe of members, so that a transfer uses all of their links at once. A stripe takes the fastest members left, as many as give it the highest rate, and the larger count where two counts tie. That rate is counted as the number of its members times the rate of the slowest, and the stripe's own rates are then measured. Each member gives its stripe the same number of bytes, as many as the smallest has, and what a larger member has beyond that is a member again. The extent devices are ranked by the rate measured beside the sweep step and filled in that order.
- *Extents and pieces.* An extent is a contiguous span of bytes on one extent device that holds one number or one array. It is dealt to the device's members in equal pieces, in turn, each piece with its check words (Section 11). A round is one piece on each member.
- *Five calls.* Every extent device offers `capacity`, `allocate`, `read`, `write`, and `free`. `read` and `write` take a list of ranges, each a span of bytes inside one extent, and move the list as one batch, so the fixed cost of reaching a device is paid once for the batch and its ranges move together. The plan sets the size of a piece so that every range is a whole number of pieces and every batch covers the members equally to within one round. A member offers the same five calls on its own bytes, and a stripe serves each call by dealing it to its members. A GPU moves its part of a batch as one submission of buffer copies, and an SSD moves its part by direct I/O, with all of its ranges in flight at once. The store moves one batch at a time, so each batch moves at the rates measured for its device.
- *Sweeps.* The column sweeps touch the store in batches of strided ranges, each range at least as large as the smallest from which a batch moves at the device's measured rates, and the row sweep is sequential. Where a tile of the store is too small for one such range from every row, the planner adds column sweeps as Section 5 describes.

**Efficiency.** Energy follows work plus traffic, so the choices above also reduce energy consumption: fewer bit operations, fewer bytes moved, and checks that detect an error where it occurs.

## 11. Correctness

Data is protected the way it is on a Micron MRDIMM, and the checks follow that implementation as closely as possible (Section 2). There, check bits are written with every word and compared with it at every read, a single erroneous bit is corrected immediately, and a larger error is reported to the system. Here, check words are written with every number, every stored piece, and the digits of every leaf, and are compared with what is read; an error inside one limb is corrected immediately, and a larger one climbs a ladder of four rungs.

| Function | On a Micron MRDIMM | suPiposition |
|---|---|---|
| Write | Check bits go with every word: 8 parity bits with every 128 data bits in the chip, and the controller's on extra chips of the module | A check word goes with every number and with the digits of every leaf, and three with every stored piece |
| Read | The check is recomputed and compared at every read | A product is compared as soon as its whole value is known, and a stored piece at every use |
| Correct | The chip corrects one wrong bit before the data leaves it, and the controller all the data of one failed device | An error inside one limb is corrected in place, and a piece of a checkpoint is reconstructed from the rest of its round |
| Retry | Parity on each command and a CRC on each write, and a retry | What fails its check is recomputed |
| Recover | Data beyond correction is marked as poisoned, and the operating system stops only its consumer | The run returns to its last checkpoint and continues |
| Scrub | On every access and in a background patrol, with counts | At every use of a piece and in the pass that writes a checkpoint, with counts |
| Exclude | A device that fails persistently is mapped out | A GPU or an SSD that fails persistently is excluded |
| Self-test | Memory and cores are tested at boot | Every assembly kernel is tested against its reference at startup |

**Check words.** There are three. The first is the number's value modulo 2⁶¹−1. It is of the whole value, so it covers the sign and, for Q, the shift count (Section 4), and it is preserved by arithmetic: the check word of a sum or a product is the sum or the product of the operands' check words. A result is therefore verified by comparing the word of what was written with the word it must have. The kernels that write a result return the first word: `fft_carry` and `ntt_crt` for the limbs they emit, `to_digits` for its digits, and `check_n` for any span of limbs. Every number carries it twice, and where the copies differ, the one that agrees with the limbs stands. Its modulus makes it shifts and additions, and gives the same weight to two bits a multiple of 61 bits apart, so the plan divides no integer into coefficients, or into parts of the outer transform, of such a length. The other two are the value modulo two of the transform's primes, 159·2⁴² + 1 and 115·2⁴² + 1, and they locate an error. The orders of 2⁶⁴ in them have a least common multiple above 2⁴⁹, so every limb of a number of up to 4×10¹⁶ bits has its own pair of weights. A wrong limb at position j changes the value by e·2⁶⁴ʲ, with e smaller than 2⁶⁴ in size; the two words leave the true pair of e and j and, in a long number, about one false pair for every 10¹⁰ limbs, and the first word selects the one that fits. Where more than one fits, the error counts as beyond one limb. A stored piece carries all three, and for a product the two are computed when the first fails.

**The ladder.** What fails a check is corrected on the lowest rung that can do so, and a rung that has failed twice at the same thing gives way to the next.

1. *Correct.* An error inside one limb is corrected in place, and so is a check word that disagrees where two others agree with the data.
2. *Recompute.* The item is recomputed from its sources, with any cached transform it uses recomputed too: once more as it was, or as an NTT product if it was an FFT product, and then with the reference kernels.
3. *Roll back.* The run returns to its last checkpoint, or to its beginning where it has none, and continues.
4. *Stop.* The run ends with a report.

Before a rung is climbed, the check words of the item and of its sources are computed again from their limbs, so that the rung is climbed by what is actually wrong: a product whose new word agrees stands, and a source whose limbs no longer agree with its word is itself the item that failed. A run that rolls back a second time for a failure at the same point, or a set number of times in all, stops, so no fault can hold a run indefinitely.

| What fails | How it shows | Where it is corrected |
|---|---|---|
| A product, a quotient, or a node of the conversion | Its check word is not the one its sources give | Rung 1 for a whole product, then rung 2 |
| The rounding of an FFT product | Its largest rounding error is over the bound | Rung 2, as an NTT product |
| A number at rest in memory | Its limbs agree with neither copy of its word, at a product that uses it or in the pass that writes a checkpoint | Rung 3 |
| A stored piece | Its data disagrees with its words, or its device cannot read it | Rung 1; then rung 3 for a piece of an extent, and rung 2, from the rest of its round, for a piece of a checkpoint |
| A piece never written, or written in the wrong place | Its own words can agree, so it shows in the number or the product it belongs to | As that number or product |
| A checkpoint or a record, as written | Read back, it disagrees | Rung 2, then the SSD that disagrees is excluded |
| A GPU or an SSD | It becomes unresponsive, its failures pass a set count, or its piece sends the run back a second time | It is excluded, and the run rolls back without it |
| The last SSD | The same | It stays, and its failures climb the ladder; if it becomes unresponsive, rung 4 |
| The checkpoint a run rolls back to | It cannot be read whole | Rung 4 |
| The output file | A write or a flush fails or does not return | Rung 4 |
| An assembly kernel | It differs from its reference at startup | Its reference takes its place |

A device is unresponsive when a call to it reports it lost, reports that a write failed, or does not return within a set time. A device that is excluded is written to the record, and a failure that excludes one does not count toward the limits on rolling back. Every correction and every failure is counted with the cores, the pages of memory, and the device that took part in it. The counts are reported at every checkpoint, at every return, and at the end of the run, and a core or a page that appears repeatedly is for the machine's operator to remove through the operating system (Section 6).

**Products.** A product is verified as soon as its whole value is known.

- *Whole.* A transform product computed in full is compared at once. An FFT product must also keep its largest rounding error within a set bound, and the two together stand in for a proof of its rounding.
- *Wrapped.* A transform shorter than the whole product folds the top of the product onto its bottom. The whole product is then the wrapped result plus 2^L − 1 times the folded part, where L is the transform's length in bits, or times one more where the fold carries out of the top and leaves the retained part all zeros. So a wrapped product is verified as soon as the check word of its folded part is known. The finish knows it beforehand: for A·z it is the upper part of u, and for 10005·u² it is all ones, or a one and zeros, because the product lies within the step's precision of one (Section 3). The conversion learns it afterward: it is the whole number that the node's left half turns into digits (Section 3). Every node hands up the check word of its digits, a leaf's from `to_digits`, and a node is verified when its left half's word arrives. Until then the node keeps its fraction, in a checkpoint too, so that its product and both halves can be recomputed.
- *In part.* The limb methods pass on a derived check word, which is verified with the first transform product that uses the result. Where they compute only part of a product, as in the first small steps of the finish, below the transforms of the conversion, and in the sequential form of the level division, the part is verified by what it leads to: the next step, the digits that the node above checks, or the quotient.
- *Quotients.* A quotient is verified through its product with the factor, because the number is the factor times the quotient. That check also covers the products that form the quotient and the factor's inverse, and where it fails, the factor and its inverse are recomputed first.

Only the methods that Section 5 marks exact may wrap a product or compute part of one. A product with no part known beforehand or handed back, such as the last product of the finish, is computed whole. Whatever part of a product is retained is given its own check word by the kernel that emits it.

**Stored pieces.** Every piece of an extent or of a checkpoint is written with all three check words, in VRAM as on SSD, because only some GPUs have error-corrected memory. In the row sweep, the workers compute a piece's words while its data is in their caches. In the column sweeps, a range is verified in a pass of `check_n` as it arrives and before it leaves, and the plan counts that pass as traffic. A piece that is corrected is written back. Every use of a piece is thus the scrub on access, and the pass that writes a checkpoint, which verifies every number at rest, is the patrol.

**Checkpoints.** A checkpoint is the set of numbers a run requires to continue from that point. One is taken when redoing the work since the last would take longer than a set multiple of the time it takes to write. The plan knows both times at every merge, Newton step, and conversion level, so only a long run writes one, and a run without an SSD writes none. A checkpoint is written to the SSDs alone, in a stripe of their own formed by the rule of Section 10, and each number is verified against its word as it goes in. The stripe takes at least two SSDs where the system has them, and one piece of every round is then the sum of the others, formed by `add_n` with the carry dropped, so any one piece, or the whole part of one SSD, can be reconstructed from the rest: the sum by `add_n`, and another by `sub_n` with the borrow dropped. On a system with one SSD, the checkpoint lies beside the extents, guarded by its check words alone. A checkpoint counts once it has been read back whole and its record is written, and the one before it is kept until then.

**The record.** The record is a checkpoint's label. It gives the digits and output requested, the shape of the stage it interrupts, the description and check word of each number, the stripe's layout and piece size, and the GPUs and SSDs excluded. For the series, the shape is the tree, which is its term count, leaf length, and dividing levels, and a number's description is its block and the factor removed so far. For the finish, the description of z and of u is their precision. For the conversion, the shape is the digits per leaf, and a fraction's description is the digits it covers and the check word that a node above requires of them. The record carries a serial number, a format version, and a check word of its own, names each GPU by the identifier its driver reports, and states in each copy which SSD the copy is on. Every SSD the run uses has two places for it: a new record is written over the older of the two and read back before it counts, so a write that is truncated or lost leaves the earlier record, and the checkpoint it describes, whole. A start therefore finds the newest whole record, under any device names and in any order, before it writes to an SSD. An SSD without a whole copy is unknown to the start: its part of a checkpoint counts as lost, and if it had been excluded, its faults exclude it again.

**Starting.** A start resumes from a record that matches its command line and its format version, and it requires the output file at its full size. Any other record, records of which none is whole, and an output file that is missing or of another size each end the start with a report, unless the command line orders the records discarded. A start that finds no record begins a new run. A resumed run takes the profile again, less the devices excluded, keeps the stage's shape, plans everything else again, and reads the checkpoint whatever stripes the new rates form. The record's places, the checkpoints still kept, and the room for the next ones lie outside what an SSD gives to the stripes of the store, so those stripes and the measuring writes stay clear of them. The digits of a leaf are written to the output file at their own offset, and the file is flushed to its device before a later checkpoint counts, so a resumed run writes only the digits its checkpoint still covers. A run that finishes flushes the output file and then clears its record.

**Against y-cruncher.** The digits of every test run are compared with those of the y-cruncher build named in Section 13, at the same size. That comparison is the check on the program as a whole, and the only one on what no check word covers: the file the digits are written to, and the program's own working state, such as the plan.

Verified by exact computation. On numbers of 4,096 and 60,000 limbs, a limb replaced by random bits, a flipped bit, and a value off by one at any bit were corrected in each of 920 trials, and two wrong limbs and a burst across eight limbs were reported as beyond one limb in each of 620. On transforms of 256 coefficients with no bits to spare in the primes' product, the first word detected each of 11,100 faults injected into whole products with coefficients of 47, 59, 60, 62, and 64 bits, and each of 10,000 injected into wrapped products of 64 coefficients at the same lengths. With coefficients of 61, 122, and 183 bits, it missed 103 of the 800 injected before the last pass of the inverse transform, which is why no coefficient has such a length. In conversions of 3,000 digits, the nodes' checks detected each of 4,314 injected faults that changed a retained digit. The first word alone misses a change that is a multiple of 2⁶¹−1, such as two bits a multiple of 61 bits apart with one set and one cleared, which is 1 pair of flipped bits in 122. The locating words detect these in a stored piece; in a product or a number in memory they pass, and are left to the comparison with y-cruncher.

## 13. Performance Model

The model takes the work to be the same on every machine and converts all arithmetic to butterflies (Section 5). It counts 8.7×10¹³ butterfly-equivalents and about 75 TiB of memory traffic for 10¹¹ digits, compared with 1.13×10¹⁴ and about 103 TiB for plain binary splitting with the same finish and conversion. The count uses the fused merge throughout (Section 4).

The table prices that one plan on two machines of the x86 target. Where traffic is the larger, the planner would move time from traffic to compute. The table uses 0.6 cycles per butterfly, which **assumes** two 512-bit multiply-add units per core. A butterfly's modular multiply is four multiply-add operations on eight residues, which two units finish in a quarter of a cycle per residue; the rounding, the add and subtract, the corrections, and the loads and stores bring the estimate to 0.6. The figures start after startup, which is the conformance run, the measurements made at every startup, and any calibration still missing.

| | One EPYC 9686F (Zen 6) | One Diamond Rapids |
|---|---|---|
| Cores | 96 | 256 |
| Clock used | 4.05 GHz (base) | 3.0 GHz (**assumed**; Intel's figure is not yet published) |
| Rated memory bandwidth | 1.64 TB/s | 1.6 TB/s |
| 10¹¹ digits: compute with ideal scaling | about 135 s | about 68 s |
| 10¹¹ digits: traffic at the rated bandwidth and at half of it | 50–101 s | 52–103 s |
| What sets the pace | Compute | Compute at the rated bandwidth; traffic below about three quarters of it |

These are lower bounds. With no overlap between moving and computing, the two times add, to about 185 s and 120 s at the rated bandwidth. Both machines remain to be tested.

**The Arm target.** The same plan runs there with two residues to a 128-bit register in place of eight to a 512-bit one, so a core issues four times the multiply-add instructions per butterfly, and its pace depends on how many 128-bit units it has and on its clock. NVIDIA gives each of Vera's cores six such units, which together hold twelve residues against the sixteen of two 512-bit units, and gives no clock; Apple publishes neither. Compute time on the Arm target is therefore left to measurement. Traffic is priced as above: at their rated 1.2 TB/s, one M5 Ultra and one Vera each move the 75 TiB in about 69 s. The M6, with at most 32 GB of memory, runs 10¹¹ digits out of core.

**Goals to test on one x86-64-v4 machine against y-cruncher v0.8.7 Build 9547 (Windows package v0.8.7.9547b, run on Windows 11):** at least 1.3× faster in memory at 10¹⁰–10¹¹ digits, and at least 1.5× faster out of core. A version that falls short of either is not released (Section 15). On a machine with a discrete GPU, there is a third test: the same out-of-core run with and without its VRAM. On the Arm target, the same runs are made on one Apple processor and on one Vera: their digits are compared with y-cruncher's, and their speeds are that target's first measurements.

## 14. Risks and Measurement Priorities

1. **Reduced splitting is counted and awaits measurement.** The divisibility is proven and verified; the net gain depends on the real cost of the level divisions, which the count prices as products at twice the quotient's length. If it falls short, the planner disables the division and the program is plain binary splitting. Separate products are counted the same way, and the planner can keep the fused merge at every node.
2. **Using all of everything is a rule that awaits measurement.** A working set that fills its cache has room only for what the design has counted. A run that takes all available RAM holds the operating system at its current size, and on a unified-memory system it holds the graphics there too, because they draw on the same pool. On a traffic-bound processor, speed may peak before the last threads join, and on an Apple processor, macOS places the workers itself, so how its slower cores share the work shows only in a run. SVE2 is likewise enabled wherever a processor has it, and at Vera's 128 bits its bodies may run no faster than the NEON ones. The first calibration runs should show what each costs, on at least one processor of each maker in the two targets. Where a measurement shows that a rule costs speed, the cost is reported with its size, and the rule stays until the project's owner changes it.
3. **The store's rates await measurement.** Whether a batch reaches a link's rate, whether the links of a stripe add, and how much a transfer and the workers slow each other are measured at startup, and an extent device that falls short ranks later in the order. A rate measured at startup stands for the whole run, and an SSD that slows as its write cache fills or as it heats moves fewer bytes than planned; the first long runs will show by how much. Only speed depends on these.
4. **Some processors are described only in part.** Diamond Rapids' multiply-add port count, L2 size, and frequency will be known when it launches, the multiply-add count for Zen 6 likewise remains to be confirmed, NVIDIA publishes the vector units of Vera's cores but not their clock, and Apple publishes neither for its cores. Only the estimates in Section 13 depend on them.
5. **The checks are counted and await measurement.** An FFT product's check word and the bound on its rounding error stand in for a proof of exactness, at about 3% of the time spent in it. What the locating words cost on stored pieces, and the digits' check word in the leaves, remains to be measured.
6. **The model counts three sweeps per product.** Where the cache shares are small against a transform, the top levels of a large run require a fourth and a fifth sweep (Section 5), with about 1.9 times the traffic at those levels.
7. **The split is counted and awaits measurement.** A single transform holds 1.82×10¹⁵ bits, which carries the series to about 3×10¹⁴ digits. A longer product takes the split, at one and a half to about two times the work of a single transform (Section 5).
8. **The model assumes ideal scaling.** Small runs on many cores will fall well short of it.
9. **The portable kernels are a specification first.** On an x86-64 processor below the target level they are exact and slow (Section 5).
10. **What no check word covers is verified only against y-cruncher** (Section 11). That is the file the digits are written to and the program's own working state.

Order of validation: the program on its reference kernels against y-cruncher's digits at 10⁶–10⁹; the reduced-splitting gain on one machine; each assembly file on processors of its target, one Intel and one AMD, one Apple and one NVIDIA; the planner on real and synthetic profiles; one GPU's VRAM against one SSD, each alone, in a stripe, and beside the workers; then out-of-core runs.

## 15. Iterative Development

Components keep each edit small, and the gates below keep it safe. An edit is accepted when it passes all four.

1. **Correct.** Every kernel meets its contract against its reference under differential fuzzing, every product matches its check word, and test runs give the same digits as y-cruncher (Section 11). These run in test builds, where contracts and overflow checks are on, and on a machine where the probe binds. On a processor with SVE2, they run once with the SVE2 bodies and once with the probe held to the NEON ones, and any entry or body that was not run is reported as untested.
2. **Correct at every scale.** The same small problems run under synthetic profiles of every size, from one core with a tiny cache to one count short of the reference machine, and those profiles force each large-run path in seconds: a tiny RAM entry sends numbers to the store, tiny caches add the extra sweeps, a short list of primes brings in the split, and calibration figures that price a checkpoint at almost nothing write one at every merge, Newton step, and conversion level. A test plan with set dividing levels and set forms brings in the factor that spans several levels and both forms of each division, merge, and split. Every row of Section 11's table is brought about deliberately and must end where the table says. A test build damages one limb, two limbs, a check word, a cached transform, or a leaf's digits; a lowered FFT bound brings in the NTT; and a wrong kernel body brings in its reference. Test members keep their bytes in ordinary memory behind the same five calls, and can fail a read, fail or drop a write, write in the wrong place, or become unresponsive; their supplied rates and unequal sizes stripe some together, leave a remainder, and rank the rest apart. The tests run on profiles with several SSDs, with one, and with none. Test numbers with runs of zeros and nines, inside the number and at its end, bring in exact digits and the report of digits in doubt (Section 3). A profile too small for the run brings in the report that it cannot be held, a test output file that cannot be created at its full size brings in the report of Section 10, and the planner's tests confirm that no plan divides a coefficient, or a part of the outer transform, at a multiple of 61 bits.
3. **Resumable.** A run is stopped at each kind of checkpoint and resumed in a new process, with its SSD members kept in files. It gives the same digits under the same profile and calibration figures and under changed ones, including rates that regroup the stripes; with the files of any one of two or more SSDs removed; and when it is stopped while it writes a record or the output file. A start is also run against every case of Section 11: a record left by another run, with and without the instruction to discard it, a record of another format version, records of which none is whole, a missing and a shortened output file, a checkpoint that cannot be read whole, and a device excluded. The record carries a format version, as the kernel table does.
4. **Faster.** The edit improves performance, whether it adds code or removes it. It is judged on a fixed set of profiles: at least one compute-bound, one traffic-bound, and one out of core. Under a supplied profile and fixed calibration figures, the plan is deterministic, so the counts of work, taken at the kernel table, and of bytes moved, taken from the modules' contracts in memory and at the extent interface in the store, are exact, and with the plan's division of each transfer between its two rates they give a planned time free of noise. An edit that changes the counts must lower that time on at least one profile and raise it on none. An edit that leaves the counts as they were, such as a faster kernel body, is timed in isolation on a fixed machine: its calibration figure must improve beyond the spread of the timing, and the planned time is recomputed with it. Work outside the kernel table, which is the sieve, is counted in its own operations, with a calibration figure, and is judged the same way. An edit that changes neither a count nor a calibration figure is judged by timed runs alone, and its gain must exceed their spread. Timed runs of the optimized build confirm every gain. The whole run is what is judged, so a gain in one module that costs another module more is rejected.

A repair is the one other kind of edit. It is accepted when it passes gates 1 to 3, restores a failing gate, a drifted contract, or a missing check, and takes no more time than what it restores requires.

**Release.** A version is released only when it meets both goals of Section 13 against y-cruncher on the same machine, and until it does, the gates continue to take edits. No version is therefore released slower than the program it is built to outperform, and if a faster π program appears, that one becomes the baseline.

The rules of Sections 6 to 9 and the model of Section 11 are fixed points of the gates: what is taken from a system, the 24 kernels, one assembly file per architecture, one body per kernel for each vector set, the standard library alone, and checks that follow error correction on a Micron MRDIMM as closely as possible. An edit that would change one goes to the owner with its measured gain.

Two practices accompany the gates. Editing is local: a language model changes one module and reads the contracts of the modules it touches. Review is global: at every release, a language model reads the whole source in one pass, looking for gains that span modules and for contracts that have drifted. What it proposes goes through the same gates.

The gates check what they exercise; what remains is for the first long runs to show.
